# Глобальный проект и подпроекты

Большая задача — один **глобальный проект** (цель, план, реестр подпроектов, решения) и несколько **подпроектов**
(каждый — своя папка, свой git, своя задача и свои сессии). Пользователь говорит только с сессией глобального проекта,
по-русски. Сессии подпроектов работают параллельно, пользователя не спрашивают, вопросы шлют в глобальную.
Шаблоны файлов и сообщений — [shablony.md](shablony.md). Общие правила — навык `sreda:kak-rabotat`.

## 1. Когда предлагать

Сразу после того, как пользователь поставил начальную задачу, если верно хотя бы одно:

- в задаче несколько независимых частей: разные программы или репозитории, разные базы, разные исполнители;
- работа на много сессий или недель, части можно вести параллельно;
- уже есть отдельные проекты, которые надо связать общей целью.

Мелкую задачу (пара файлов, одна сессия) в эту схему не раскладывать.

Как предлагать — по правилам «решить и показать»: в тексте — какие подпроекты вижу, что каждый отдаёт, почему так
быстрее и надёжнее; само предложение — окном с кнопками: «Разложить на глобальный проект и подпроекты
(рекомендую)» / «Вести одним проектом». Ничего не создавать до «да».

## 2. Устройство глобального проекта

Отдельная папка со своим git. Кода подпроектов в ней нет — только ссылки на них.

| Файл | Что в нём |
|---|---|
| `CLAUDE.md` | Что за проект; с чего начать сессию; сверка подпроектов; порядок общения; как создать подпроект; правила заказчика или ссылки на них |
| `docs/План.md` | Цель и требования пользователя **дословно, с номерами R1, R2…**; порядок работы; этапы и сроки |
| `docs/Подпроекты.md` | Реестр: где лежит, **GitHub**, что **отдаёт глобальному**, ссылка на задание, состояние, **коммит и дата последней сверки**, последняя отправка |
| `docs/Задания/<Подпроект>.md` | Задания для подпроектов, которые уже были отдельными репозиториями (глобальный в чужих репозиториях не пишет) |
| `docs/adr/` | Решения: что выбрано, почему, чьё решение и когда |
| `docs/Передача_сессии.md` | Где остановились и что дальше — обновлять в конце сессии и при передаче контекста |
| `GLOSSARY.md` | Термины проекта |

Первые решения записать ADR, когда пользователь согласился: устройство глобального проекта (связь через реестр со
сверкой, а не копированием) и порядок общения (раздел 5).

## 3. Новый подпроект

1. Папка подпроекта со своим git (рядом с глобальным, например `<корень проектов>\<Имя>`).
2. `CLAUDE.md` подпроекта, первой строкой: «Подпроект <Глобальный>: что от него ждут — `<путь к реестру>`».
3. `docs/Задание.md`: слова пользователя дословно (цитаты по-русски), исходные данные, что сделать, **что вернуть**,
   **как проверить**, зона (где писать, чего не трогать), срок. Для существующего репозитория задание лежит в
   глобальном (`docs/Задания/<Имя>.md`), подпроект его читает.
4. Строка в реестр глобального. Коммит в глобальном и в подпроекте. Закрытый репозиторий в GitHub — сразу, если
   пользователь уже велел держать проекты в GitHub (раздел 7); адрес — в реестр.
5. Сессия подпроекта — отдельная, в его папке (`start_session` с папкой подпроекта, новый контекст): короткий бриф
   по-английски со ссылкой на задание. Запускать, когда пользователь согласился с планом и перечнем подпроектов.

Общее для нескольких подпроектов (инструменты, библиотеки) — отдельный общий репозиторий, а не копии.

## 4. Работа сессий

- **Глобальная сессия** ведёт план и реестр, раздаёт задания, принимает результаты, передаёт вопросы. Файлы
  подпроектов только читает: их меняют их собственные сессии (исключение — `git push` за подпроект без сессии, раздел 7).
- **Сессия подпроекта** работает по заданию в своей зоне, коммитит в свой git, в конце — отчёт глобальной (5–15
  строк по-английски: что сделано, где, коммит или PR, что не проверено, что нужно от пользователя). Крупные находки —
  в файлы подпроекта или в общую папку заметок группы сессий, в сообщении — путь.
- Обе ведут контекст коротким: мод `autohandoff`, документ передачи; глобальная переходит в новую сессию по
  `docs/Передача_сессии.md`. Сессии подпроектов — так же, со своим файлом передачи. Пороги в тысячах токенов:
  подпроект — со 150 (с 250 — без проверки момента), глобальная — со 150 (с 200); перед передачей — отсчёт с паузой; мод узнаёт глобальную по
  `docs/Подпроекты.md` в её папке. Почему — `sreda:kak-rabotat`, раздел 9.
- **Внутри подпроекта** чтение и проверки — субагентами (много прочитать, мало вернуть); новый подпроект — только для
  части, которая живёт много сессий и ждёт решений пользователя.
- **Координация — дешевле**: глобальная сессия почти вся из переписки, и каждое её действие читает её целиком.
  Вопросы подпроекта копить и слать пачкой в конце шага, а не по одному; глобальная задаёт их пользователю одним окном
  (до 4) и отвечает подпроекту одним сообщением.
- Слияние PR подпроекта — только по «да» пользователя на этот PR; спрашивает глобальная.

## 5. Порядок общения

1. **Пользователь ↔ глобальная сессия — по-русски.** Вопросы ему — окном с кнопками, подпроект — в `header`
   окна; в панель «Ждут ответа» вопрос окна попадает сам (файл панели вручную не писать).
2. **Глобальная ↔ подпроекты — по-английски** (сообщения между сессиями: задания, вопросы, отчёты). По-русски
   остаются слова пользователя (цитаты дословно), документы для людей (ADR, спецификации, тексты экранов, отчёты
   пользователю) и комментарии в коде, как принято в репозитории.
3. **Подпроект пользователя не спрашивает.** Вопрос → одним коротким сообщением в глобальную: что решаем, варианты,
   рекомендация и почему. Глобальная проверяет, не решено ли это уже (план, ADR, ответы другим подпроектам), иначе
   задаёт окном и передаёт ответ обратно — дословно, по-русски, с переводом.
4. В начале сессии глобальная смотрит открытые вопросы в панели и напоминает о неотвеченных.

## 6. Приёмка и сверка

- **Приёмка** — по тому, что подпроект должен вернуть: независимая проверка свежим субагентом против задания и слов
  пользователя (без отчёта подпроекта как подсказки). Принято — обновить реестр (состояние, коммит, дата) и план;
  пользователю — коротко, что готово и что не проверено.
- **Сверка подпроектов** — по просьбе пользователя или не чаще раза в день (не в каждой сессии), и только тех
  подпроектов, где с прошлой сверки были коммиты или отчёт; по каждой такой строке реестра:
  1. `git -C <путь> log --oneline <коммит сверки>..<ветка>` и `git -C <путь> status -s` — что изменилось и что не
     закоммичено.
  2. Его файл передачи, README, новые ADR — изменилось ли то, что он отдаёт глобальному.
  3. Затронут план — отметить в плане и в передаче; новое противоречие — показать пользователю.
  4. Записать в реестр новый коммит сверки и дату; коммит в глобальном.

## 7. Отправка в GitHub — всех сразу

Пользователь велит глобальному проекту закоммитить и отправить («commit and push», «отправь в GitHub») — это команда
**для глобального и для всех подпроектов реестра**: пользователю не нужно следить за каждым. Так же — «отправь всё».
**Контролирует всё глобальная**: кто занят, кто отправил, кто ещё должен — до последнего подпроекта.

1. **Глобальный** — коммит своего и отправка.
2. **Сначала — кто чем занят.** По каждому подпроекту глобальная смотрит состояние его сессии (список связанных
   сессий: работает или ждёт) и `git status`. Свободной сессии — сразу: закоммитить законченное, отправить, доложить.
   **Занятой** (идут вычисления, перенос данных, долгая операция, запись в базу) — та же команда, но «после того как
   закончится текущая операция»: не прерывать, не коммитить за неё и не отправлять её папку, пока она работает.
   Сомнение, занята ли, — считать занятой. Что считать законченным, решает сам подпроект: недоделку он не коммитит,
   а сообщает о ней в отчёте. Шаблон сообщения — [shablony.md](shablony.md). Сессия прочитает его после текущего хода
   и отправит сама; глобальная просит уведомить, когда та освободится (`SendMessage` с `notify_when_idle`).
3. **Подпроект без работающей сессии** (закончена, в архиве): незакоммиченного нет — глобальная отправляет сама
   (только `git push`, файлы и коммиты не трогает); незакоммиченное есть — не коммитить чужую работу, показать
   пользователю, что и где.
4. **Нет репозитория в GitHub** — создать **закрытый** (`gh repo create <владелец>/<имя латиницей> --private`), но
   сначала проверить **всю историю**, а не только текущие файлы: `git grep -I -n -i -E '<образцы>' $(git rev-list
   --all)` — ключи и токены (`ghp_`, `sk-`, `AKIA`, `PRIVATE KEY`, токены ботов), «password/пароль/token = значение»,
   телефоны, почта; и список файлов (`git ls-files`) — выгрузки баз, `.env`, `.pfx`, `.pem`, таблицы с данными.
   Каждое совпадение просмотреть: примеры и тестовые данные — можно, настоящие — не отправлять, показать
   пользователю. Открытый — только по прямому слову пользователя, и тогда без имён клиентов (вместо них «База_N»).
5. **Без силы:** без `--force`, без переписывания истории, без слияния PR (слияние — по «да» на каждый PR); если
   отправка отклонена (на GitHub есть чужие коммиты) — подпроект сам подтягивает и отправляет снова. Отправляются
   только рабочие ветки подпроекта (обычно текущая); черновые и чужие — нет.
6. **Сводка пользователю** одной таблицей: проект, ветка, коммит, отправлено ли; что ещё не отправлено и почему
   (сессия в работе, нашлись секреты, незакоммиченное без сессии).
7. **Довести до конца.** Ждущие подпроекты — список в `docs/Передача_сессии.md` (переживает передачу контекста).
   Глобальная отмечает каждый, когда тот доложил, и проверяет сама (`git -C <путь> status -sb`: нет «ahead»). Не
   доложил, когда освободился, или к началу следующей сессии глобальной — напомнить ему; сессия закончилась, а работа не отправлена — пункт 3. Все
   отправлены — одна короткая строка пользователю: «отправка закончена».
8. **Реестр:** у каждой строки — адрес GitHub и дата и коммит последней отправки; коммит и отправка глобального.
