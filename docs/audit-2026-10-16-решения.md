### П01. Не включать навыки 1С везде, а только в проектах 1С

Набор `1c-skills` — это 81 навык, и он включён глобально. Список навыков переполняется, и у многих навыков модель
видит только имя без описания: у `delivery-control`, `diagnose`, `ui-icons`, `data-skills`. Предлагается выключить
`1c-skills` в общем шаблоне и включать его в `.claude/settings.json` проектов 1С. Затем проверить в новой сессии,
что описания видны. Если не делать — свои навыки не будут срабатывать сами, только когда их прямо назовёт CLAUDE.md.

### П02. Поднимать версию плагина при каждой правке и вести CHANGELOG

`onec-odata` изменён, а версия осталась `1.0.0`. Claude Code хранит плагины по номеру версии, поэтому машины, где
плагин уже стоит, правку не получат. Предлагается: поднять `onec-odata` до `1.0.1`, завести `CHANGELOG.md`, выпускать
версии командой `claude plugin tag`. Если не делать — правки своих плагинов будут теряться на части компьютеров.

### П03. Защитить ветку main на GitHub

Установщики, шаблоны и свои плагины берутся прямо из `main`, и у всех включено автообновление. Предлагается:

### П04. Автоматическая проверка в CI на каждый PR

Сейчас проверок нет. Предлагается добавить GitHub Actions, которые на каждый PR:
- запускают `claude plugin validate --strict`;
- проверяют JSON;
- проверяют скрипты через shellcheck и PSScriptAnalyzer;
- запускают оба установщика во временной папке на Windows и Ubuntu;
- проверяют, что у изменённого плагина поднята версия и что в навыках нет битых ссылок.

Если не делать — ошибки в манифестах и установщиках будут видны только после установки у пользователей.

### П06. Не скрывать сбой установки Python-пакетов на Linux

На новых Debian и Ubuntu команда `pip install --user` отказывается работать, а ошибка скрыта. Это касается хука в
шаблоне проекта и `install.sh`. Предлагается: при отказе повторять с `--break-system-packages` (или ставить через
uv/venv), а при неудаче выводить одну понятную строку. Если не делать — `1c-skills-py` в облаке может не работать,
и никто не узнает почему.

### П07. install.sh: брать шаблоны из клона и обновлять адрес маркетплейса

`install.sh` всегда скачивает шаблоны из сети, даже при запуске из клона: правку нельзя проверить до пуша.
Кроме того, оба установщика при повторном запуске не меняют уже записанные значения. У тех, кто ставил раньше,
остался старый адрес маркетплейса через SSH. Предлагается: читать локальные шаблоны, если они рядом. Для своей
записи `xebcyp-plugins` обновлять адрес, для остальных записей показывать расхождение с шаблоном. Если не делать —
на старых машинах обновления могут требовать SSH-ключ.
Отчёт: находки 6 и 7, план шаг 6. Объём: **мелко**.

### П08. Короче описать delivery-control и убрать из навыка «разрешение дано заранее»

Описание навыка пересказывает весь процесс. По опыту superpowers, агент тогда выполняет описание и не читает сам
навык. Предлагается оставить в описании только условия срабатывания. Фразу о заранее данном разрешении на
субагентов перенести в CLAUDE.md пользователя, где она уже есть. В навыке оставить: «разрешил — не спрашивать,
иначе спросить один раз». Если не делать — процесс выполняется не полностью, а чужие пользователи маркетплейса
получают разрешение, которого не давали.
