# Аудит маркетплейса xebcyp-plugins — 2026-10-16

Проверено: `.claude-plugin/marketplace.json`, плагины `onec-odata`, `data-skills`, `ui-icons`, `delivery-control`,
закрепления `1c-skills`, `1c-skills-py`, `bsl-language-server`, `dbhub`, `AUDIT.md`, `README.md`, `templates/`,
`scripts/install.ps1`, `scripts/install.sh`. Репозиторий не менялся, кроме этого файла.

## Резюме

- **Манифесты корректны.** `claude plugin validate` (2.1.299), в том числе `--strict`, проходит для маркетплейса и
  всех четырёх своих плагинов; есть только совет добавить строку установки в `plugins/data-skills/README.md`.
- **Закрепления свежие.** Все `sha` сторонних плагинов совпадают с текущим HEAD исходных репозиториев
  (`git ls-remote`); `@theyahia/aprovodka` 4.3.0 и `@bytebase/dbhub` 1.5.0 — последние версии в npm. Клоны
  nick-vels/skills, obra/superpowers и mattpocock/skills в `C:\Data` тоже совпадают с HEAD.
- **Установщики работают** (проверены во временной `CLAUDE_CONFIG_DIR`: PowerShell 5.1, pwsh 7, bash): чужие
  ключи сохраняются, блок в CLAUDE.md ставится и заменяется, повторный запуск ничего не дублирует.
- **Главные проблемы:** описания навыков не доходят до модели из-за перегрузки списка навыков (1c-skills —
  81 навык глобально); нет дисциплины версий (правка `onec-odata` без смены версии); вся цепочка доставки идёт
  из `main` без закрепления; нет тестов навыков, CHANGELOG и CI.

## Находки (по убыванию важности)

### 1. Высокая — описания своих навыков не попадают в контекст модели
- **Где:** `templates/user-settings.json:18` (`1c-skills` включён глобально), `templates/project-settings.json:17`.
- **Что:** в этой сессии в списке навыков описания есть у `1c-skills` до `role-validate`, а у остальных
  `1c-skills` (`mxl-*`, `skd-*`, `xdto-*`…), всех `data-skills`, `ui-icons`, `delivery-control`, `diagnose` описания
  нет, только имя. По `claude plugin details` постоянная нагрузка: 1c-skills ~3,5 тыс. токенов, data-skills ~885,
  onec-tools ~589, delivery-control ~316, ui-icons ~148.
- **Риск:** модель сама не вызывает `ui-icons`, `data-skills` и половину навыков 1С. `delivery-control` и
  `diagnose` срабатывают только потому, что их прямо называет CLAUDE.md.
- **Исправление:** `1c-skills` (или `-py`) включать в проектах 1С через `.claude/settings.json` проекта, а в
  глобальном шаблоне выключить. Описания своих навыков сократить до условий срабатывания (см. п. 8). После
  этого проверить в новой сессии, что описания показываются.

### 2. Высокая — версия плагина не меняется вместе с содержимым
- **Где:** `plugins/onec-odata/.claude-plugin/plugin.json:4`. Коммит `b65eb4e` изменил `userConfig.password`,
  а версия осталась `1.0.0`.
- **Риск:** Claude Code кэширует свои плагины по `version` (`~/.claude/plugins/cache/xebcyp-plugins/<плагин>/1.0.0`).
  Если версия не сменилась, машины, поставившие плагин раньше, правку не получат. С `ui-icons 1.0.0` и
  `data-skills 1.1.0` будет то же при первой правке.
- **Исправление:** правило «изменил плагин — поднял `version`», выпуск через `claude plugin tag`, проверка в CI
  (п. 15). Образец — `C:\Data\mattpocock-skills\scripts\sync-plugin-version.mjs`.

### 3. Средняя — всё доставляется из `main` без закрепления
- **Где:** `README.md:23,29` (`irm … | iex`, `curl … | bash` с `main`), `templates/user-settings.json:8`
  (`autoUpdate: true`), `scripts/install.ps1:13,57`, `scripts/install.sh:9,39`.
- **Риск:** один ошибочный или чужой пуш в `main` (например, в `onec-odata/.mcp.json`, который запускает `npx`)
  при следующем старте исполняется на всех подключённых машинах и в облаке. Закрепление по `sha` защищает от
  сторонних репозиториев, но не от своего.
- **Исправление:** защитить `main` на GitHub (только PR, обязательный CI, 2FA, по возможности подписанные
  коммиты). В README давать ссылку на скрипт по тегу. CI с `validate --strict` — обязательная проверка PR.

### 4. Средняя — у `onec-odata` нет воспроизводимой сборки
- **Где:** `plugins/onec-odata/.mcp.json:5` (`npx -y @theyahia/aprovodka@4.3.0`); `AUDIT.md:42-46`.
- **Что:** закреплена только верхняя версия, транзитивные `@modelcontextprotocol/sdk`, `express`, `zod`
  подбираются по диапазонам при каждой установке. Исходников пакета на GitHub нет — проверен только архив npm.
- **Риск:** новая транзитивная версия попадёт к пользователям без проверки. Этот сервер получает пароль 1С
  и умеет писать в базу.
- **Исправление:** обёртка в плагине с `package.json` и `package-lock.json` (`npm ci --ignore-scripts`, запуск
  из `${CLAUDE_PLUGIN_ROOT}`) или собранный бандл. Минимум — `npm audit signatures` и перепроверка дерева
  зависимостей при каждом обновлении `AUDIT.md`.

### 5. Средняя — `pip install --user` молча падает на новых Linux
- **Где:** `templates/project-settings.json:31` (хук SessionStart), `scripts/install.sh:60`.
- **Риск:** на Debian 12 и Ubuntu 23.04+ (PEP 668) `pip install --user` без `--break-system-packages`
  отказывает; ошибку глушат `>/dev/null 2>&1 || true`. Без `lxml` навыки `1c-skills-py` не работают, а
  сообщения об ошибке пользователь не увидит. В облаке не проверялось (см. «Что не проверено»).
- **Исправление:** при отказе повторять с `--break-system-packages` (или ставить через `uv`/venv), а при
  неудаче писать одну строку в stderr, без `>/dev/null`.

### 6. Средняя — `install.sh` всегда берёт шаблоны из сети
- **Где:** `scripts/install.sh:13,40`. Для сравнения, `install.ps1:14-20,58-64` при запуске из клона читает
  локальные `templates/`.
- **Риск:** правку шаблона нельзя проверить на Linux до пуша; при запуске из клона без сети скрипт падает.
- **Исправление:** как в ps1 — если рядом есть `../templates/…`, читать оттуда.

### 7. Средняя — повторный запуск не обновляет уже записанные значения
- **Где:** `scripts/install.ps1:39`, `scripts/install.sh:28` (добавляются только отсутствующие ключи);
  `README.md:32-34`.
- **Риск:** у тех, кто ставил до `de51d6e`, остаётся `"source": "github"` (SSH), и повторный запуск его не
  меняет. README обещает, что «плагины будут обновляться», а про то, что настройки не обновляются, молчит.
- **Исправление:** для записи `extraKnownMarketplaces.xebcyp-plugins` заменять `source` на значение из шаблона
  (запись своя), для остальных ключей — показывать расхождение с шаблоном.

### 8. Средняя — описание `delivery-control` пересказывает процесс, а навык сам объявляет разрешение
- **Где:** `plugins/delivery-control/skills/delivery-control/SKILL.md:3` (описание в 689 знаков, почти всё —
  пересказ шагов), `:102-103` («Разрешение на субагентов … пользователь дал заранее, когда включил этот навык»).
- **Риск:** по `obra-superpowers/skills/writing-skills/SKILL.md:150-158`, если описание пересказывает процесс,
  агент выполняет описание и не читает тело навыка. Описание в одну строку дешевле для п. 1. Фраза о
  разрешении для других пользователей маркетплейса не очевидна: само включение навыка они согласием не считают.
- **Исправление:** в описании оставить только ветки срабатывания, по одной на ветку (writing-for-agents,
  «One trigger per branch»): «Использовать в начале задачи больше пары файлов или с несколькими
  требованиями, перед „готово“, при замечаниях ревью, когда просят проверить, ничего ли не потеряно». Разрешение
  оставить в CLAUDE.md пользователя (оно там уже есть, `templates/user-CLAUDE.md:10-12`), в навыке написать «если
  пользователь разрешил заранее — не спрашивать, иначе спросить один раз».

### 9. Средняя — не сказано, что правила навыков 1С о базах тоже главнее

  а не в CLAUDE.md проекта, приоритет неоднозначен.
- **Исправление:** в обоих навыках написать: «правила других включённых навыков о запусках на базах и учётных
  решениях (onec-tools, 1c-skills `db-*`) тоже главнее». Других противоречий не нашёл: про свод правил

### 11. Низкая — мелкие недочёты установщиков

- **Исправление:** делать резервную копию только перед записью, если файл меняется. В ps1 на 5.1 писать через
  pwsh, если он есть. В sh открывать файл с `encoding="utf-8-sig"`. В ps1 обернуть тело в `& { … }`.

## Что не проверено и почему

- **`irm | iex` и `curl | bash` целиком не запускались:** скрипт выполнил бы `gh auth setup-git` и изменил
  настоящий `~/.gitconfig`, а `install.sh` — `pip install --user` в настоящий профиль. Я прогонял копии без этих
  строк во временной `CLAUDE_CONFIG_DIR`. Для `irm` отдельно проверил только, что кириллица скачивается без
  искажений.
- **`install.sh` не проверялся на настоящих Linux и macOS:** прогон шёл в Git Bash на Windows, `python3`
  подменялся обёрткой над `python`. Отказ pip из-за PEP 668 (п. 5) выведен из известного поведения pip; в облаке
  Claude Code не воспроизводился.
- **Код `1c-skills`, `bsl-language-server`, `dbhub` и пакета aprovodka заново не читался:** их sha и версии не
  изменились с проверки в `AUDIT.md` того же дня, выводы взяты оттуда. Режим `ONEC_WRITE_MODE=approval` на живой
  базе не проверялся: подключения к базе нет.
- **Срабатывание навыков на сценариях не прогонялось:** готовых `evals/` нет, а `claude -p` или
  `claude plugin eval` по установленным плагинам работали бы на настоящем `~/.claude`, с его хуками (например,
  с загрузкой bsl-language-server). Вывод п. 1 сделан по одной сессии: список навыков, который видел я сам.
- **Устаревание закреплений** проверено только сравнением с HEAD (`git ls-remote`, `npm view`); новые коммиты
  не просматривались, потому что их нет.
